# Webhook operations

Use a human CLI session as the subscription's original creator. Never delegate destination operations to an agent. Inspection/rotation require current `webhooks:create`; replay/re-drive require current `webhooks:replay`.

1. Inspect terminal evidence with `octocove webhook deliveries ID --status parked --json` or `--status cancelled`. Page with `--after` using `nextAfter`; limit is 1–100, default 50. Inspection is audited and returns identifiers, attempt count, deadline and last HTTP status only.
2. Investigate receiver reachability and restore the creator's membership if revoked. Automatic suspension emits system `webhook.disabled` evidence. Membership restoration alone does not resume sends.
3. If disabled, call `octocove webhook reactivate ID --idempotency-key KEY`. Then explicitly call `octocove webhook redrive ID --delivery DELIVERY --idempotency-key ANOTHER_KEY`. The original parked/cancelled row stays terminal; a new replay preserves its event ID and gets a fresh delivery window. Event dedupe is required at the receiver.
4. For a wider recovery range use creator-only `webhook replay ID --after CURSOR --through CURSOR`.

For signing rotation, generate a fresh base64 secret of at least 32 random bytes and install it in the receiver first. Pipe it through stdin to `octocove webhook rotate-secret ID --secret-stdin --overlap-seconds 300 --idempotency-key KEY --json`. Bind the returned `signingKeyId` to the new secret. Retain the previous ID/secret until `overlapUntil` (Unix seconds), then remove it. Receivers should stage the new key and buffer unknown-generation requests until the rotation receipt supplies its ID if rotation races receipt delivery. Each attempt has exactly one signature; select the named key, verify raw bytes and timestamp, and reject the previous ID at expiry. Retries prepare with the current key; requests prepared before rotation can use the previous key during overlap. Retry the same request/key for a lost response. A changed body/key conflict or a second rotation during overlap is 409. An already issued request cannot be revoked. Encryption vault keyring maintenance follows the separate API rewrap procedure.

Configure `RECOVERY_ALERT_URL` (trusted HTTPS operations sink) and `RECOVERY_ALERT_TOKEN`. Recovery sweeps drain up to 50 parked-window alerts, using `webhook-window-<deliveryId>` as sink idempotency key. Monitor `webhook-window-alert-failed`; unconfigured/failing sinks never receive an acknowledgement row. Query `webhook_delivery_alerts` for acknowledged delivery IDs. The sink must dedupe; a crash after acceptance can resend. Alerts contain no signing secret, event body, URL or arbitrary transport error. Dispatch and inspection preserve SSRF, pinned TLS and revocation checks. No live configuration or external operations are required to validate this runbook locally.

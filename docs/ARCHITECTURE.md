# Architecture

The control-plane record, authentication, audit writer and task lifecycle live in `apps/control-plane`, with the integrator (`apps/integrator`) and CLI (`packages/cli`). Core collaboration paths are tested locally on Miniflare/D1 and native Git; separate live Artifacts probes do not qualify a complete deployed service.

Storage: D1 holds the collaboration record, one Durable Object per task coordinates it, and Artifacts (or a registered BYO provider) holds git. Artifacts is not the only copy of canonical history; see [BACKUP.md](BACKUP.md).

## Contract

A task carries versioned human intent and acceptance criteria. Agents submit immutable submissions; the host builds a tested integration candidate; a human approval binds the exact `(candidate SHA, base SHA, intent version)`; landing is reconciled against the canonical remote and produces an attributable receipt. A dependent task is admitted only after its upstream is accepted **and landed**. A stale base means recompute and re-review, never a silent overwrite.

## Components

- **Control-plane Worker + D1** (`apps/control-plane`): coordination API, event/approval path, provisioning, Queue consumer. D1 holds intent, submissions and audit state.
- **Token broker**: issues short-lived, task-scoped, repo-scoped delegated tokens to agents after a human session authorizes a claim. Upstream Artifacts credentials stay server-side.
- **Trusted native-git integrator** (`apps/integrator`): runs as a bounded Job from a Docker image on an operator-provisioned container host, through the container dispatcher. The same image is portable to Cloudflare Containers or a VM, but a native-git run on Containers is not qualified. The runner is configured explicitly; there is no silent failover between runners. It is the only holder of the canonical write token. Fetches the candidate, integrates, and pushes canonical `main` with `--force-with-lease`, so two concurrent landings cannot silently overwrite each other (one wins, the other reports `raced` and returns to review).
- **Artifacts** as the git substrate.
- **Identity**: humans sign in through the configured OIDC provider via OIDC. Octocove's dependency on it is an OIDC client registration, not code.

## Topology

Fork per task is not the default topology: on Artifacts, forking a 200 MB repository takes 23.7 s at p95 against a 5 s target, and `repo.forked` is not reliably delivered. Artifacts-hosted canonicals use chain-mode repo lanes ([ADR 0003](adr/0003-chain-mode-repo-lanes.md)); canonicals on a BYO provider use ref lanes ([ADR 0010](adr/0010-byo-canonical-provider.md)).

The bounded smart-HTTP gateway exists at [`apps/gateway/src/worker.mjs`](../apps/gateway/src/worker.mjs). It enforces whole-request ref policy before forwarding, but is **not enabled in claim provisioning or the production broker**. Protocol/size limits and the private broker contract are in the [gateway guide](../apps/gateway/README.md). Local workerd and live Artifacts latency figures are not deployed-edge qualification; local proof/helper controls do not establish client-runtime isolation ([ADR 0005](adr/0005-credential-boundary.md)).

Chain mode is implemented under [ADR 0003](adr/0003-chain-mode-repo-lanes.md): D1 pool/pointer/writer lease, asynchronous exact-base attach, durable pending-push queue and receipt/custody-gated retirement. The chain driver is qualified against local D1/DO and bare Git only, not production RTT, distributed provider behavior or durable pod hosting. The implemented pool default is four; the recommended stocked-burst configuration is at least eight. Combined-path and sustained-refill behaviour is not qualified, and worker-side refresh is not measured. Compatible per-task forks and BYO/external ref paths remain available within their documented provider restrictions.

For the compatible fork path, `TaskRepoProvisioner` defines provisioning, subscription and release. `ForkTaskRepoProvisioner` uses REST fork with `default_branch_only: true`, subscribes to `pushed`, and confirms asynchronous deletion with GET → 404. Fork REST responses and reconciliation establish readiness; `repo.forked` never does.

Claim provisioning is asynchronous. POST claim and bootstrap claim commit the granted attempt and return **202 pending**; the alarm reserves a durable attempt, releases the task queue while awaiting the provider, then re-enters the queue to recheck authority and commit the mapping/broker grant. A 200 MB fork takes **7–24 s (p95 23.7 s)** and scales with repo size, so requests and intent edits must remain responsive during a fork. A 45 s timeout, durable lease and exponential retry backoff bound each attempt; five failures produce `blocked` with a fixed reason. Release, takeover and expiry during provider I/O prevent readiness from being committed. The fork's REST response (`id, remote, token, objects`) supplies readiness, with GET repo reconciliation after ambiguous responses; fork tokens are discarded. **`repo.forked` is never a readiness or reconciliation dependency**, because the provider does not reliably deliver it. CLI clients poll GET claim before configuring a remote; the web shows “Provisioning…”.

## Collaboration record

The record (intent history, task, claim attempts, submissions with context snapshots, candidates with check runs, approvals bound to `(candidate SHA, base SHA, intent version)`, the landing fence, landing receipts, append-only audit log) is specified field by field in [COLLABORATION_RECORD.md](COLLABORATION_RECORD.md), with the D1 schema in `apps/control-plane/migrations/0001_record.sql` and the invariant test list in `tests/record-invariants.todo.md`.

## Audit row

actor, taskId, lane ref or task repo, sourceSha, baseSha, candidateSha, approval {by, at, boundTo}, landedSha, event ids consumed, intent version. Stored as `audit_log` rows per transition (see [record §10](COLLABORATION_RECORD.md#10-audit-log)).

## Boundary with the external credential helper

`git-credential-artifacts` is a separate git credential helper, not part of this repository and not published; this repository contains none of its source. It only asks the control plane for repo-scoped tokens, keyed by host and path, and answers git's credential protocol. It contains no collaboration logic, no integrator code and no schema. The token-broker HTTP endpoint is the only interface between them; Octocove's side of it is specified in [HELPER_BROKER_CONTRACT.md](HELPER_BROKER_CONTRACT.md). The socket transport that allocated claims use (`packages/helper`, [ADR 0005](adr/0005-credential-boundary.md)) is part of this repository.

## Implemented task coordination

`TaskCoordinator` is a Durable Object **per task** (`idFromName(taskId)`, `apps/control-plane/src/index.ts`). It holds a serial promise across D1 and provider awaits; D1 unique indexes and conditional mutations provide additional guards. Alarms do local work inside that queue and release it before any cross-task call. Cross-task effects (canonical base moves, receipts, dependent re-evaluation) travel as committed D1 outbox rows with stable command keys; a delivery is acknowledged only after the receiving task commits, so reciprocal calls cannot hold each other's queue and a crash replays the receiving task's stored result. **Per-target landing serialization is not a DO property:** the unique partial index `canonical_one_held_fence` on `(repository_id, ref_name)` for held fences ([`migrations/0008_canonical_delivery_custody.sql:26`](../apps/control-plane/migrations/0008_canonical_delivery_custody.sql#L26 "CREATE UNIQUE INDEX canonical_one_held_fence")), fed by trigger `canonical_fence_acquired` in the same batch as tuple validation, audit and dispatch, admits one held fence per target; a losing admission rolls everything back. Durable canonical generations order evidence across task DOs, and the native-git expected-old lease remains the final ref-write guard. `TaskLifecycle` is the trusted domain API shared by HTTP and internal adapters. All effective record transitions use `appendTransitions` from the audit writer (`apps/control-plane/src/audit.ts`); snapshots, operation results and outbox rows commit in the same batch. Task status remains distinct from claim/candidate/approval status.

Claim admission freezes upstream accepted receipt IDs and landed SHAs. Auth preauthorization reserves the claim/delegation IDs; lifecycle consumes the bootstrap with the persisted attempt and calls `AuthService.issueDelegation` after grant. Unidentifiable credentials never invent claim actors. Authenticated business refusals are persisted. Provider calls occur after admission; deterministic claim-based names reconcile ambiguous fork/subscription responses, with pending/blocked state exposed through claim polling. Provisioning commits the project/canonical/task-repo/ref mapping and a credential-free `claim_broker_grants` row together. The token broker consumes this authorization table (grant ID, claim ID, mapping ID, project, canonical/task repository IDs, target ref, expiry, revocation); lifecycle never returns a provider token.

Approvals bind the immutable candidate/base/intent triple. Fencing checks the shared canonical head again inside the D1 mutation. During a held fence, new intent rows and submissions carry its ID and leave the fenced authorization intact. Only an authenticated, run-bound integrator reconciliation with terminated writer and fetched-object ancestry may release a successful fence. An unknown writer stays fenced. Receipt audit evidence is sufficient for the existing standalone receipt renderer. Staged work queues a fresh candidate after release, requiring its own approval; follow-up candidates never reopen or change a landed task's accepted receipt.

An alarm is scheduled before public mutation admission. Durable outbox jobs use stable run IDs and at-least-once delivery. Integrator consumers must deduplicate run IDs. Cleanup retries asynchronous deletion and retains the task repo until staged objects have been captured by the integrator. Revocation/expiry immediately closes broker grants without releasing an in-flight landing fence. Dependency reevaluation and base invalidation are routed to the affected task's own coordinator. Internal adapters call `invokeTaskCommand`; its task/command/key/body capability is signed with a domain-separated HMAC using the configured auth recovery key. Public routes never expose this internal transport. Integrator signature and canonical-object verification belong to the integrator adapter, before it calls this trusted boundary; a client-provided reconciliation body is never accepted directly.

Local acceptance uses Vitest, Miniflare Durable Objects and local D1, plus a fake Artifacts HTTP server. It does not claim live Artifacts latency, isolation, event-delivery or CAS evidence.

## Events consumer (Artifacts → observations)

`src/events.ts` is the Workers-native Queue consumer (`queue()` export in `src/index.ts`; consumer binding on `octocove-events` in `wrangler.jsonc`). It handles `repo.pushed`, `repo.forked` and `repo.deleted`. Two phases, both safe to repeat, so a redelivery after a crash completes the work instead of skipping it:

1. **Observe.** Normalise the payload, then insert one immutable `push_observations` row plus its `observation.recorded` audit row in one batch. Routing uses the durable `task_repo_mappings` row for `(repository, ref)`, never an active grant or claim. A push is never attributed to an actor and never creates a submission; only an authenticated `submit` does. With no matching submission the observation is flagged `unsubmitted-push`; pairing is one-to-one with the oldest unclaimed submission of that commit (trigger `submission_pairs_observation` covers a submit that arrives after the push). Unknown repo, or a known repo with no live mapping, is recorded as `unknown-repo`, logged, and acknowledged. `repo.deleted` also stamps `repositories.deleted_at`, which stops the broker minting for it.
2. **Follow up.** `before != last known head` for the mapping (last observation, else last submission) schedules a reconciliation: a fresh ref read using a read token minted through the broker (`BrokerRemoteReader`, a per-run `integrator-read` grant), recorded as an `ls-remote` observation flagged `reconcile`. It is evidence, not a verdict. A push on a landing target flags `canonical`, reads the fresh head, moves `target_refs` forward only in time, and routes `baseMoved` to each open task's coordinator; the existing base-move rule invalidates only approvals bound to a different base. A matched submission invalidates an `active`, unfenced approval only when it is **newer by submission `seq`** than the approval's own submission and no fence is held; fenced approvals, approvals newer than the observation and unsubmitted pushes (INV-36) never change.

**Transport identity.** The deduplication key is the provider event id if the payload carries one (`id`/`eventId`). The live Artifacts payload field name is not documented, so the parser tolerates several names. Absent an id, it is a SHA-256 of (event timestamp, repo, ref, before, after, kind), and absent a timestamp too, the queue message id. It is never `(repo, ref, after)`: A→B→A produces two observations and two submissions.

**Poison messages.** Malformed bodies (bad SHA, missing repo/ref) and messages that exhaust `maxAttempts` (5) are parked in `poison_messages` (migration `0006_events.sql`) and acknowledged; the `alert` hook is called, and `alerted_at` is set only if it succeeds. Unrecognised event types are ignored and logged. Canonical reconciliation of a repo with no recorded remote needs `ARTIFACTS_GIT_REMOTE_TEMPLATE` (`{namespace}`, `{name}`); without it the message retries, then parks.

Tests (`tests/events.test.ts`) use a fake queue over Miniflare D1: duplicate, out-of-order, A→B→A, unknown repo, reconciliation trigger, poison parking, approval invalidation (older-only, fenced untouched) and canonical base-move. They do not exercise live Artifacts delivery or the smart-HTTP ref read.

Receipt refs are projections of the immutable D1 `landing_receipts` record. Migration `0017_receipt_export.sql` inserts a `receipt_export_outbox` row by trigger in each new receipt transaction. The task DO recovery alarm, scheduled before the record commit, queues pending exports until their signed completion is recorded. The existing queue/container dispatcher native integrator path uses a stable `receipt-export-<receiptId>` run, independent of released landing fences and terminal task grants.

Before dispatch, the control plane persists a small JSON blob containing the authoritative receipt row, a version and authority marker, and an HMAC-SHA256 signature over `receipt-export:<payload>` using `INTEGRATOR_RUN_SECRET`. The envelope's exact UTF-8 bytes and Git blob SHA are immutable after first preparation, including across key rotation. Signature verification requires the trusted signing key; possession of a ref is never approval evidence. Deploy the migration and updated control/runner protocol together.

The broker derives an export-only grant from that pending outbox row. It binds the canonical repository and exact `refs/octocove/receipts/<receiptId>` ref, advertises only the receipts prefix, records credential handles without plaintext, and rechecks after provider mint I/O. Artifacts tokens remain repository-scoped: the trusted native exporter enforces the ref scope, as for candidate grants. It hashes the persisted bytes, reads the ref, and creates it with an expected-absence lease. A matching ref is a no-op; any different value produces terminal `export-conflict`, never an overwrite. Export completion only updates outbox bookkeeping and revokes export tokens; it cannot create receipts, approvals or dependency releases. Transient failures leave the row pending for alarm recovery. A crash after push but before completion replays the same SHA.

CLI `receipt show` and web receipt views continue to read the control-plane/D1 record. Missing, delayed or conflicting projections do not change acceptance, and readers must never infer approval or landed state from Git receipt refs. `apps/control-plane/tests/receipt-export.test.ts` covers record-before-export and push-before-export-completion crashes, duplicate delivery, immutable signed content, prefix/repository denial, and conflict preservation with local D1 and bare Git repos (20 repetitions).

# Documentation index

This Apache-2.0 repository contains the Octocove CLI, client library, credential helper and shared packages, a frozen copy of the Worker server engine under [`server/`](../server/README.md) and of the API contract under [`spec/`](../spec/openapi.yaml) ([frozen paths](PUBLIC_SCOPE.md#frozen-paths)), the conformance harness and this documentation. The server implements the record API using Workers, D1, Durable Objects, queues and Artifacts ([public scope](PUBLIC_SCOPE.md)). The hosted service provides the web application; the server guide describes the verified local API boot path and authentication prerequisites.

## Install and use

Start with the root [README](../README.md) and [contribution setup](../CONTRIBUTING.md#setup): Node 22, pnpm 10.34.5, frozen-lockfile install and single-file checks. The [CLI guide](../packages/cli/README.md) describes commands and configuration, and the [client library guide](../packages/client/README.md) the TypeScript client. Package tests and the [conformance harness](../tools/conformance/README.md) run against fixtures and provider doubles; they are not live-provider qualification of a deployed service.

Package guides: [CLI](../packages/cli/README.md), [client](../packages/client/README.md), [helper](../packages/helper/README.md), [shared](../packages/shared/README.md). Headless machine clients (a CI approver, a bot): [machine clients](examples/machine-clients.md).

## How the client talks to the service

Every client (a workspace adapter, an agent in its own clone through the CLI, CI with a policy-bot approver) reaches an Octocove deployment through four public surfaces. Nothing else in the service is part of the contract.

- **HTTP API.** One record API for humans and agents, specified by [`spec/openapi.yaml`](../spec/openapi.yaml) and described in [API.md](API.md): projects, repositories, tasks, claims, candidates, approvals, landings and their receipts. Writes carry an `Idempotency-Key`, and asynchronous results are read back from the record. [`packages/client`](../packages/client/README.md) is generated from the spec (operations, routing and a retry policy per operation), and the CLI is built on it. The record's nouns, states and transitions are specified in [COLLABORATION_RECORD.md](COLLABORATION_RECORD.md); authentication (sessions, agent delegations, machine identities, browser origins) in [AUTH.md](AUTH.md).
- **Events and webhooks.** Recorded changes are published as versioned v1 events ([ADR 0004](adr/0004-event-vocabulary.md)). A client either pulls them with `GET /events` and a cursor, or subscribes a webhook endpoint that receives the same signed envelope ([ADR 0006](adr/0006-webhook-operations.md), [ADR 0008](adr/0008-replay-retention-and-cursor-rotation.md), [webhook runbook](runbooks/webhook-operations.md)). An event says that something was recorded; the client then reads the authoritative state and decides what to do. Events never schedule work.
- **Helper/broker contract.** A writer never holds a reusable Git credential. The local credential helper ([`packages/helper`](../packages/helper/README.md)) holds the attempt's grant and exchanges it with the service's token broker, as specified in [HELPER_BROKER_CONTRACT.md](HELPER_BROKER_CONTRACT.md) under [ADR 0005](adr/0005-credential-boundary.md); [API.md](API.md#repo-scoped-token-broker) describes the broker routes. The [credential boundary runbook](runbooks/credential-boundary.md) covers setup per client runtime.
- **Git transport.** Source moves over the native Git protocol. An agent in its own clone pushes to its own repository and registers the exact candidate commit ([ADR 0002](adr/0002-own-clone-source-registration.md)); an allocated lane is reached through the helper's `ext::octocove-helper-connect` transport ([ADR 0003](adr/0003-chain-mode-repo-lanes.md), [ADR 0010](adr/0010-byo-canonical-provider.md)). Landing into the canonical repository is done by the service, and the result is recorded as an attributable receipt ([ADR 0011](adr/0011-receipt-ref-export.md)).

The [generic client contract](reference/CLIENT_CONTRACT.md) states what each client archetype must do on these surfaces; the conformance harness checks it.
